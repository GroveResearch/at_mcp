# Decisions

One line per project ruling or load-bearing design decision. Each carries the date it landed, a status (settled / provisional / retired), the evidence that holds it, and, where it compensates for a defect somewhere else, what would retire it. A line marked `unverified` has a written reason but no test or code that would fail if it stopped being true. Dates are the commit that made the decision real; `git log -S` finds the rest.

## Current name

- 2026-10-02 · settled (deepfates, #111) · The package, OTP app and release are `at_mcp`; the Elixir namespace is `AtMcp`. An agent connects its own persistent AT Protocol identity. The old private repository and history stay private; a future public repository is a separately reviewed snapshot. Commands and environment names change explicitly (README, "Transition from Kite 0.1.2"); saved file names, formats and published MCP tool names remain unchanged. The `x-kite-account-did` header, `kite/publicWrite` annotation and bearer token prefix remain because existing clients and grants use them. The historical entries below retain their original names and evidence coordinates; current code lives under `lib/at_mcp` and tests under `test/at_mcp`.

## Ownership

- 2026-09-09 · settled · Kite owns one AT Protocol account per DID (one process per configured account today; aliases of a DID are the provisional exception under Writes): credentials, session and refresh, readiness and disconnect, the durable per-DID write quota, the MCP tool surface, and durable delivery of incoming activity. It does not own conversations, permission decisions or an agent's behavior. — `AGENTS.md`; `Kite.Effects`; `test/kite/effects_identity_test.exs`.
- 2026-09-13 · settled · Kite bounds writes per account per hour and never per turn; host tokens, `/turns`, `KITE_MAX_WRITES_PER_TURN` and per-turn counters were deleted, not flagged. — `Kite.Identities.start_identity_runtime/1` raises on turn options; `test/kite/account_quota_boundary_test.exs`.
- 2026-09-11 · settled · Which identities an installation holds is answered by an operator listener (`KITE_CONTROL_PORT`), not by an MCP tool, and the answer carries no credential. — `Kite.Control`; `test/kite/telos_test.exs` "no tool lets an agent enumerate the installation's identities".
- 2026-09-06 · settled · One tool a person does not have exists on purpose: `identity_status` (session and write quota). — `Kite.MCP.Server`; `test/kite/mcp_tools_test.exs`.
- 2026-09-23 · settled (owner) · There is no tool for declining to act; an agent that ends its turn without calling a write tool has not posted. — `Kite.MCP.Server`; `test/kite/mcp_tools_test.exs` "every tool returns structured content its declared schema accepts" lists the whole surface.
- 2026-09-10 · provisional · Lists, starter packs, pinned posts, thread gates, self-labels, reporting, bookmarks and direct messages are deferred until each arrives with the controls that make it safe; whether an agent may post an undescribed image is the owner's call. — `docs/DESIGN.md`; unverified (no test names the absence).

## Credentials and access

- 2026-10-05 · provisional (#5) · Explicit `AT_MCP_APPVIEW_READS=direct` routes application GETs requiring an AppView through short-lived method-bound service tokens. Default proxy routing, PDS-owned preferences and all writes retain their current paths. Fixed Network endpoints bound the prototype; arbitrary providers remain unproved. This qualifies the historical every-read-via-session-service rule below. — `AtMcp.ATProto.ServiceAuth`; `test/at_mcp/direct_service_auth_test.exs`.


- 2026-09-11 · settled · One loopback MCP endpoint (`KITE_MCP_PORT`, 4400) serves every identity; `Authorization: Bearer <grant>` decides which identity a request acts as; a request with no grant is `401`, never served. — `Kite.MCP.HTTP`; `test/kite/mcp_http_test.exs` "the endpoint refuses a caller that presents nothing"; `test/kite/telos_test.exs` "one endpoint serves every identity".
- 2026-09-11 · settled · `x-kite-account-did` confirms the binding and selects nothing. — `Kite.MCP.HTTP`; `test/kite/mcp_http_test.exs` "one listener serves every identity, and a grant reaches only its own".
- 2026-09-11 · settled · A grant's scope (`read` / `write` / `manage`) is derived from each tool's own `readOnlyHint` and `destructiveHint`, never from a hand-kept verb list; a tool with no hints is reached by no scope. — `Kite.Grants`; `test/kite/mcp_http_test.exs` "a grant's scope bounds the tools it reaches, from the tools' own hints".
- 2026-09-11 · settled · Grants live in their own 0600 file beside the accounts file and store only digests; deleting that file revokes everything and keeps every identity; removing an account revokes its grants. — `Kite.Grants`; `test/kite/grants_test.exs`.
- 2026-09-11 · settled · No authorization server, no TLS requirement, no introspection endpoint. The OAuth resource-server code was deleted rather than kept behind a flag. Bearer is kept as the shape so an issuer-signed token can arrive later without a client changing. — no `oauth` in `lib/`; `Kite.Grants` moduledoc.
- 2026-09-11 · settled (owner) · No OAuth, MCP's or ATProto's, for now; login is an app password. Retires when there is a multi-tenant reason, which is Haven's question rather than Kite's. — workshop `AGENTS.md` standing decisions.
- 2026-09-07 · settled · `kite-connect` is a stdio front onto the shared service and holds no account password. — `test/kite/shared_stdio_test.exs`; `test/kite/account_setup_test.exs`.
- 2026-09-11 · settled · `kite-connect` receives its grant in `KITE_GRANT`, never in argv. — `Kite.SharedConnection`; `test/kite/account_setup_test.exs` ("Not in argv, where every process on the machine could read it"); `test/kite/shared_stdio_test.exs`.
- 2026-09-11 · settled · A grant is a bearer token on loopback with no binding to the holding process: it separates what each client was given, not what each process could obtain. It is not a sandbox, and the write quota is not an authorization boundary. — `Kite.Grants` moduledoc; unverified as a test.

## Configuration

- 2026-09-11 · settled · An installation is configured one way: the accounts file that `kite-accounts` manages (`KITE_ACCOUNTS_FILE`, or the platform's user configuration directory). No environment variable adds, removes or reauthorizes an account behind it. — `test/kite/telos_test.exs` "an installation is configured one way".
- 2026-09-11 · settled · `BLUESKY_HANDLE` / `BLUESKY_APP_PASSWORD` (and the `_2` pair) are read once, only when no accounts file exists, to write one; a login that fails writes nothing. — `Kite.AccountSetup`; `test/kite/account_setup_test.exs` "an installation configured by BLUESKY_* migrates itself into the accounts file".
- 2026-09-11 · provisional · An accounts file that still carries a per-account `mcp_port` loads with the key dropped, because refusing it as corrupt would lose an operator their accounts; a caller passing one is refused; the next write leaves it out. Retire the line once no installation predates the one-endpoint cutover. — `Kite.AccountConfig`; `test/kite/account_config_test.exs` "a file that still carries per-account ports loads without them".
- 2026-09-11 · settled · A missing accounts file is an installation with no accounts and the service still starts; a file that cannot be read is reported as unreadable, never as empty. — `test/kite/telos_test.exs` "a configuration that cannot be read is reported as unreadable, not as empty".
- 2026-09-07 · settled · Private files (the accounts file first; grants, quota and state followed) are written 0600, read-modify-write under one lock; an insecure file or symlink is refused. — `test/kite/account_config_test.exs` "insecure files and symlinks rejected".
- 2026-09-11 · settled · That file handling lives in one module, `Kite.PrivateFile`, not repeated per store. — `Kite.PrivateFile`; `Kite.AccountConfig` and `Kite.Grants` call it.
- 2026-09-07 · settled · `kite-mcp` (stdio) owns a single-account runtime, stops on EOF, opens no port and collects nothing; it reads `KITE_STDIO_ENV_FILE` and ignores the service's `KITE_ENV_FILE`. — `Kite.Stdio`; `test/kite/stdio_startup_test.exs`; `test/kite/stdio_test.exs`.
- 2026-09-12 · settled · A network is installation-wide; reaching Bluesky and Delvetown at once is two installations, each with its own unit, environment file, accounts file, ports, grants and `RELEASE_NODE`. — `Kite.Network`; README "Run it", "A second installation"; `test/kite/account_release_test.exs` (a second installation runs beside the first).
- 2026-09-28 · settled · Erlang distribution is the release's local control channel (`rpc`, `remote`), never a transport between machines, and it uses no port mapper: a mapper shared by Kite, Dwell and Haven belonged to whichever release started it, and under systemd died with that unit. The service listens on 127.0.0.1 at `KITE_DIST_PORT` (4370 by default; Dwell 4380, Haven 4390), `rpc` and `remote` connect straight to it and listen on nothing, and a second installation sets its own port. OTP still offers the node's name to a mapper on 127.0.0.1 if one is running; nothing depends on it. A node name without a host is given a loopback one (`localhost`, or `127.0.0.1` under `RELEASE_DISTRIBUTION=name`), because the machine's hostname can resolve to an address where nothing listens. `eval` gets no port. — `rel/vm.args.eex`, `rel/remote.vm.args.eex`, `rel/env.sh.eex`; `scripts/foreground_boot_check.py` (started as the example plist starts it, with no mapper reachable, every operator command answers and the node listens on 127.0.0.1 alone); `test/kite/account_release_test.exs` "release account commands manage one daemon across live configuration changes" (with no mapper reachable, every operator command works; the service listens only on 127.0.0.1 at its distribution port and MCP endpoint; a second installation runs beside it) and "the distribution port is 4370 unless the environment file names another, and eval gets none".
- 2026-09-07 · retired 2026-09-29 · The service commands ship inside the release on its bundled runtime, and start and restart wait for application readiness rather than trusting the service manager's acceptance. — `test/kite/service_test.exs`. Retired: the service is the release's own `bin/kite start` under a unit from `rel/examples/`; `kite-service` is deleted (GroveResearch/kite#92).
- 2026-09-25 · retired 2026-09-29 · Kite installs and upgrades like ordinary software, and the owner's machine does what a stranger's does. `kite install` records the installation (`DATA/installations/LABEL.json`, DATA per `Kite.Installation.paths/3`: label, configuration file, accounts file, state directory, port, current and previous release) and every later command reads it: `kite upgrade [--release TAG|PATH]`, `kite rollback`, `kite status`, `kite-service`, `kite-accounts`, with no environment variable or installation path at the call site. A literal `app.bsky` anywhere else in `lib/` is a defect. `com.atproto.*` and `chat.bsky.*` stay literal because the rename does not touch them. — `test/kite/network_test.exs`; `test/kite/telos_test.exs` "the network Kite talks to is a value, not a literal".

- 2026-09-11 · settled · Kite builds every record it writes (`Kite.ATProto`) and sends it with `com.atproto.repo.createRecord`; nothing in `lib/` calls `ProtoRune.Bsky` or `Repo.create_record/3`. - 2026-09-11 · settled · Every read goes through `Kite.ATProto` with the session's own service URL, so no read reaches Bluesky by default for an account hosted elsewhere. Compensates for proto_rune's fixed `default_base_url` and `plc.directory` resolver. — `test/kite/network_test.exs` "every declared read and write carries the namespace"; `test/kite/pds_test.exs`.

## Writes

- 2026-09-29 · settled · Only publishing counts against the write quota: `post`, `reply` and `repost` reserve, and every other write (like, unlike, unrepost, follow, unfollow, block, unblock, mute, unmute, delete_post, update_profile, update_seen) goes out without spending one. The classification is `Kite.Effects.publishing/0`; each write tool's `kite/publicWrite` annotation and the sentence its description ends with derive from it. · The quota exists to bound what an account publishes; on the first night of the model residents, likes and follows spent it within minutes and real replies waited for the reset (owner, GroveResearch/kite#99). — `test/kite/publishing_quota_test.exs`.
- 2026-09-06 · settled · One durable write quota per DID, 16 attempted writes per hour by default (publishing writes only since 2026-09-29), shared by every client, alias and reconnect; attempted writes count even when the remote call fails; reads do not. — `Kite.WriteQuota`; `test/kite/write_quota_test.exs` "remote failure counts against the write quota"; `test/kite/shared_http_quota_test.exs`.
- 2026-09-06 · settled · The write quota ledger is monotonic (`max(clock, last_seen)`): a clock moved back cannot open a fresh window; a clock moved forward keeps the window closed until real time catches up. That is the safe direction and not worth machinery. — `Kite.WriteQuota` moduledoc; `test/kite/write_quota_test.exs` (clock fixture, "damaged quota state never resets an account's write quota").
- 2026-09-08 · settled · Kite's failure vocabulary has four kinds. A backend reports one of three — refused, credential refused, indeterminate — and any reason of another shape is indeterminate; the fourth, unreadable, says the service answered and Kite's own parsing, in `Kite.Effects.ProtoRune`, could not read the answer; it is never a classification of a service's error. Only the backend classifies its service's errors: nothing above it reads status codes or error text. — `Kite.Effects.Failure`; `test/kite/backend_failure_test.exs`.
- 2026-09-07 · settled · An indeterminate write outcome is reported as `outcome: "unknown"` and never retried; only a refused credential (the backend's `:auth_refused`, for reads as for writes) triggers session recovery, and the retry after recovery takes its own write quota slot. — `test/kite/write_outcome_test.exs` "committed writes with lost responses stay unknown without retry or leaking backend details".
- 2026-09-24 · settled · Every account call answers within `Kite.Effects.call_deadline/0`, which is shorter than the MCP endpoint's handler timeout, so no tool call ends in ExMCP's bare `handler_timeout`: at the deadline a write that reached the backend is `write_outcome_unknown`, and anything else — including a write still waiting behind another — is `call_deadline_exceeded`, which changed nothing. A task marks a write as sent before its last deadline check, so a caller that gives up without the mark is never followed by the write; a write stopped at that check is reported unknown, the safe side. The longest a caller waits is `Kite.Effects.answered_within/0` (the deadline plus twice the owner's grace), and the endpoint's timeout is derived from it. — `test/kite/call_deadline_test.exs`; `test/kite/account_owner_test.exs` "a write queued behind a slow write is not sent once its deadline passes", "a caller that stops waiting is never told nothing changed about a write that is then sent", "the longest a caller waits is answered_within/0, and the endpoint waits longer".
- 2026-09-24 · settled · One process owns each configured account (`Kite.Effects`; not yet each DID, see the provisional line below) and does its work in tasks linked to it: writes one at a time in the order they arrive, reads alongside them without waiting, and one login or refresh at a time whose result every waiting call shares. There is no lock a caller waits on. When the owner stops, its work stops: a write already sent is `write_outcome_unknown`, a call not yet started is `account_runtime_unavailable`. — `test/kite/account_owner_test.exs`; `test/kite/session_ownership_test.exs`; `test/kite/call_deadline_test.exs` "a reply is sent while a read the service never answers is still waiting".
- 2026-09-24 · provisional · The owner is per configured account, not per DID. Two account entries that log in to the same DID (aliases) each have their own `Kite.Effects`, so writes to that DID through different aliases run in parallel and in no order relative to each other, `update_seen` included (two aliases marking notifications seen can finish out of order); within one alias they are ordered. The write quota is already per DID and bounds them together. Retires when one owner serves every alias of a DID, which needs the lifecycle owner to bind an alias to the DID's owner once its login reveals the DID. — unverified (no test names the limit).
- 2026-09-07 · settled · Post and reply text is validated against the network's grapheme and byte limits before the write quota is charged. — `test/kite/post_validation_test.exs`; `test/kite/network_test.exs` "bound what Kite refuses before it sends anything".
- 2026-09-28 · settled · A follow, block, mute or unmute resolves its handle to a DID before the write quota is charged and before anything is sent, so a handle the service could not resolve (a 400 `HandleNotFound` or `InvalidRequest`, or a string that is not a handle) is refused as `handle_not_resolved` at no cost, never reported as an unknown outcome; any other failure of that read keeps its own kind and also costs nothing. Every tool that takes a handle drops one leading `@`. — `Kite.Effects.Backend.resolve_actor/2`; `test/kite/actor_resolution_test.exs`.
- 2026-09-07 · settled · Rich text preserves the supplied text and adds facets for resolved `@handle` mentions, explicit HTTP(S) links and hashtags; an unresolved handle stays plain and is named in `unresolved_mentions`; bare domains and cashtags are not detected. — `test/kite/rich_text_test.exs`.
- 2026-09-07 · settled · Summaries keep the viewer's like/repost/follow/block record URIs so an agent can undo without the original receipt; a missing viewer object is distinct from an empty one. — `test/kite/summary_test.exs` "an absent viewer stays absent and an empty one stays empty"; `test/kite/viewer_context_test.exs`.

## Collection and delivery

- 2026-09-13 · settled · Account notification polling is the ordinary collector (60 s interval, five-minute overlap, private per-DID checkpoint that advances only after a complete retained scan, never marks anything read); the first poll looks back five minutes, not the whole inbox. — `Kite.Notifications`; `test/kite/notifications_test.exs`; `test/kite/collection_config_test.exs`.
- 2026-09-06 · settled · Jetstream is opt-in (`KITE_JETSTREAM=1`), subscribes with an empty `wanted_dids` and matches recipients locally, because incoming interactions are records in somebody else's repository. — `Kite.Stream.Jetstream`; `test/kite/stream_jetstream_test.exs` "an inbox cannot be a DID filter"; `test/kite/inbound_match_test.exs`.
- 2026-09-09 · settled · Collection sits behind `Kite.Stream`; an adapter owns its service's options, message shape and event fields. Jetstream v2 is a new adapter, not a change to collection, matching, the store or delivery. — `Kite.Stream`; `test/support/fake_stream.ex`.
- 2026-09-13 · settled · Delivery is a consumer-neutral HTTP POST of the normalized event to `KITE_DELIVERY_URL` with a bearer token re-read per delivery; the event names its network.
